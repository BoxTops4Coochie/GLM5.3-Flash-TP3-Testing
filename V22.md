# v22 - Zero-overhead refined expert placement

v22 keeps the validated v19 TP3/EP3 + KDA W8A16 execution path, but changes how the 288 routed experts are assigned to the three EP ranks.

The goal was to reduce per-layer MoE rank imbalance without adding a decode-time expert-remapping kernel.

```text
v19
-> profile TP3 collectives / MoE skew (v20, profiling only)
-> test runtime logical->physical remap (v21)
-> measure runtime lookup overhead with identity control
-> move the same mapping entirely to load time
-> v22 zero-overhead refined placement
```

**Local image:** `voipmonitor/vllm:glm53-native-tp3-bf16-v22-refined-zero-overhead`

**Recommended public tag when published:** `azallaza/glm53-tp3-testing:v22-refined-zero-overhead`

v20 and v21 were development/profiling images only and do not need separate documentation files.

---

# What v20 and v21 established

## v20 - profiling-only collective / MoE instrumentation

v20 was a child of v19 used to instrument TP/EP collectives and MoE phases. It was not intended as a serving image.

The source-level accounting and Nsight traces established the decode collective structure:

```text
1 input-embedding TP AllReduce
45 attention o_proj TP AllReduce
3 dense-MLP down-projection TP AllReduce
42 sparse-MoE final TP AllReduce
---------------------------------
91 AllReduce / generated token

plus:

1 logits AllGather / generated token
```

The strongest repeatable rank-arrival skew was generated inside the sparse MoE phase rather than by the collective implementation itself. The active NVFP4 backend was FlashInfer CUTLASS with contiguous physical expert ownership:

```text
EP0: physical experts   0..95
EP1: physical experts  96..191
EP2: physical experts 192..287
```

World-size-3 communication remained PyNCCL because the tested alternative all-reduce backends did not support this geometry.

## v21 - runtime remap prototype

v21 tested the refined logical expert placement by adding a cached logical-to-physical lookup in the router during every sparse layer.

Correctness passed, but the production result was effectively flat because the runtime indexed gather consumed the small load-balance gain.

Same 512-token benchmark:

```text
v21 refined runtime remap: ~111.06 tok/s
v21 identity lookup:       ~111.02 tok/s
v19 baseline:              ~111.91 tok/s
```

The identity control showed that the runtime lookup itself cost roughly 0.8% relative to the v19 baseline.

That led directly to v22: keep the refined ownership, but remove the decode-time lookup completely.

# v22 design

The checkpoint has:

```text
routed experts:          288
experts selected/token:    8
EP ranks:                  3
physical experts/rank:    96

n_group:                   1
topk_group:                1
topk_method:               noaux_tc
router dtype:              float32
norm_topk_prob:            true
routed_scaling_factor:     2.5
```

Because `n_group=1` and `topk_group=1`, all experts are in the same routing group. A consistent permutation of router output channels, correction bias, and loaded expert weights therefore preserves routing semantics while changing which physical EP rank owns each logical expert.

v22 performs that permutation only while loading the model. There is **no logical-to-physical gather in the decode router**.

# How v22 encodes the placement

Two inverse permutations are used:

```text
L2P = logical expert -> physical expert
P2L = physical expert -> logical expert
```

Physical expert slots remain contiguous to FlashInfer:

```text
physical 0..95     -> EP0
physical 96..191   -> EP1
physical 192..287  -> EP2
```

Only the logical expert content stored in those physical slots changes.

Example:

```text
logical expert 2 -> physical 0   -> EP0
logical expert 1 -> physical 96  -> EP1
logical expert 0 -> physical 192 -> EP2
```

## Router load-time permutation

During `Glm5Next` weight loading, v22 intercepts sparse router tensors after the normal GLM weight-name remap.

For each sparse layer, `.mlp.gate.weight` has shape `[288, 4096]` and is reordered on output/expert dimension 0 using `P2L`.

The router correction bias `.mlp.gate.e_score_correction_bias` has shape `[288]` and is reordered by the same `P2L` permutation.

Conceptually:

```python
loaded_weight = loaded_weight.index_select(0, P2L)
```

The router therefore emits the **physical** expert IDs directly. No runtime mapping is required.

## Routed-expert weight loading

The routed-expert loader preserves the original logical expert ID for checkpoint semantics and ModelOpt scale handling:

```text
global_expert_id = logical checkpoint expert ID
physical_expert_id = L2P[global_expert_id]
```

The physical ID is then passed through the normal contiguous EP-local mapping, while the original logical `global_expert_id` is retained for ModelOpt global-scale indexing.

# Determinism investigation and fix

Repeated greedy requests exposed run-to-run differences in the target model before sampling.

The diagnostic request used:

```text
temperature:                  0
top_p:                        1.0
top_k:                       -1
seed:                         0
max_tokens:                   1
routed_experts_prompt_start:  0
```

The returned routed-expert tensor had shape:

```text
(33, 45, 8)
```

## FlashInfer CUTLASS with autotune enabled

With FlashInfer autotuning enabled, repeated requests produced different routed-expert tensors and different first-token log probabilities.

The differences existed before the autoregressive trajectory had time to diverge, so the sampler was not the root cause.

Alternative backend checks showed:

```text
FLASHINFER_CUTLASS + autotune ON -> strongly nondeterministic
HUMMING                         -> less variation, still nondeterministic
EMULATION                       -> deterministic
```

## FlashInfer CUTLASS with autotune disabled

Removing the single launcher flag:

```text
--enable-flashinfer-autotune
```

eliminated the observed nondeterminism while keeping the same target MoE backend.

Twenty repeated routed-expert captures produced:

```text
runs:                20
shape:               (33, 45, 8)
unique hashes:       1
identical to run 1:  20/20
min differences:     0
max differences:     0
mean differences:    0.0

first token:         "3"
logprob:             -0.1603407859802246
logprob spread:      0.000000
```

The same configuration then passed the full 256-token arithmetic control:

```text
20 / 20 PASS
expected answer: 38000
```

This remained deterministic after requesting `FULL` CUDA graphs.

The GLM GDN backend automatically resolved:

```text
FULL -> FULL_DECODE_ONLY
```

so decode is graph-captured while prefill remains eager.

The startup log explicitly confirms:

```text
enable_flashinfer_autotune=False
Using 'FLASHINFER_CUTLASS' NvFp4 MoE backend
Skipping FlashInfer autotune because it is disabled.
```

This is the final v22 serving behavior.

# Conclusion

v22 remains the stable exact-TP3/EP3 implementation with zero-overhead refined expert placement.

The refreshed baseline adds three important conclusions:

```text
1. FlashInfer CUTLASS itself is usable and deterministic.
2. FlashInfer autotuning was the source of the observed run-to-run target-MoE variation.
3. Vision remains fully functional after disabling autotune and adds effectively no decode penalty.
```

The final general-purpose configuration is:

```text
TP3 / EP3
vision enabled
max_num_seqs = 8
max_num_batched_tokens = 8192
gpu_memory_utilization = 0.95
FLASHINFER_CUTLASS target MoE
FlashInfer autotune OFF
KDA Triton
FULL requested -> FULL_DECODE_ONLY
```

The old standalone prefill and concurrency sections have intentionally been removed from this refreshed document so the headline validation reflects only the final deterministic target configuration.

The next work should proceed from this frozen baseline:

```text
1. requalify MTP1 / MTP2 / MTP3 with autotune OFF
2. compare acceptance / correctness / decode speed
3. evaluate selected Infernix/LIL TP3 improvements
4. add DFlash2
5. revisit smaller conventional tuning afterward
```

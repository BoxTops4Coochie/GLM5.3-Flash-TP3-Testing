# v17 - Official template/parser correctness and performance baseline

**Prebuilt image (public, no login required):** `docker pull azallaza/glm53-tp3-testing:v17-official-template-parser`
→ replaces the local build `voipmonitor/vllm:glm53-native-tp3-bf16-v17-official-template-parser`.

v17 is the current confirmed GLM-5.3 Flash native TP3/EP3 correctness and decode-performance baseline on 3× RTX PRO 6000 Blackwell GPUs.

---

## What changed from v16

v16 did not have its own image because it was a configuration-only test using the v15 image.

That test removed the custom minimal template and allowed the checkpoint/default template to render the prompt. The deterministic arithmetic test changed from the custom-template failure:

```text
17 * 23 -> 289289
```

to the correct result:

```text
17 * 23 -> 391
```

v17 made the clean configuration the reference path:

```text
v14 shared-expert correctness fix: retained
custom minimal template:           removed
official/default checkpoint template: restored
reasoning parser:                  glm45 restored
tool-call parser:                  glm47 retained
vision:                            disabled
MTP / DFlash:                      disabled
```

The TP3 KDA/MLA/vocab padding and EP3 routed-expert work were unchanged.

---

## Correctness validation

Arithmetic test:

```bash
curl -s http://127.0.0.1:15015/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "GLM-5.3-Flash-TP3",
    "messages": [{"role":"user","content":"What is 17 * 23? Answer only with the number."}],
    "temperature": 0,
    "max_tokens": 64
  }' | jq '.choices[0].message'
```

Observed result:

```json
{
  "role": "assistant",
  "content": "391",
  "refusal": null,
  "reasoning": "17 * 23 = 391\n\nLet me verify: 17 * 23 = 17 * 20 + 17 * 3 = 340 + 51 = 391"
}
```

Long-decode validation was also performed with a 2048-token technical/networking prompt. Generation remained coherent for the complete budget and stopped because of:

```text
finish_reason = length
```

This is materially different from pre-v14, where output often degraded after only a few dozen decode tokens.

# Current v17 compose

The current v17 runtime uses the model's native 1M context window and `max_num_seqs=1` for the single-request decode measurements.

```yaml
services:
  glm53-native-tp3:
    image: voipmonitor/vllm:glm53-native-tp3-bf16-v17-official-template-parser
    container_name: glm53-native-tp3
    restart: "no"

    ipc: host
    shm_size: "64gb"

    ports:
      - "15015:8000"

    volumes:
      - /m2-2/huggingface:/root/.cache/huggingface

    environment:
      HF_HUB_OFFLINE: "1"
      GLM53_DEBUG_KDA_STATE: "0"
      GLM53_DEBUG_MLA_HEADS: "0"
      GLM53_DEBUG_INDEXER: "0"

    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              device_ids: ["0", "1", "2"]
              capabilities: [gpu]

    command:
      - LibertAIDAI/GLM-5.3-Flash-NVFP4
      - --tensor-parallel-size
      - "3"
      - --enable-expert-parallel
      - --language-model-only
      - --max-model-len
      - "1048576"
      - --max-num-seqs
      - "1"
      - --max-num-batched-tokens
      - "2048"
      - --gpu-memory-utilization
      - "0.95"
      - --kv-cache-dtype

      - auto
      - --enable-flashinfer-autotune
      - --additional-config
      - '{"glm53_kda_decode_backend":"triton"}'
```

Important launcher/runtime defaults underneath the explicit compose overrides:

```text

```

```text

available KV-cache memory: ~24.39 GiB/GPU
GPU KV-cache capacity:     4,134,385 tokens
1M max concurrency:        3.94x
peak activation memory:    ~3.68 GiB/GPU

captured graph sizes:      [1, 2]
```

During profiling, CUDA graph capture was estimated at approximately:

```text
1.46 GiB/GPU
```

but the finalized graph pool was only about:

```text

```

The baseline deliberately keeps:

```text
--gpu-memory-utilization 0.95
```

No additional memory-utilization tuning is included.

# Backend / communication experiments

## Custom all-reduce

B12X PCIe custom all-reduce in this stack does not support TP world size 3.

Observed supported world sizes:

```text
2, 4, 6, 8, 12, 16
```

TP3 therefore falls back to PyNCCL/NCCL, and the baseline keeps:

```text
--disable-custom-all-reduce
```

## KDA decode backend

Triton remained the best tested option.

Approximate warm results:

```text
Triton: ~95.6 tok/s with the tuned baseline
B12X:   ~90.5 tok/s
```

`auto` did not materially beat explicit Triton after warmup.

## NCCL protocol tests

Working inherited baseline observed ring + LL behavior.

Alternatives were slower:

```text
LL128-only: ~89.4 tok/s
Simple-only: ~87.5 tok/s
```

A 2-channel test was effectively identical to the 4-channel baseline and was reverted.

## MoE backend

`auto` selects:

```text
FLASHINFER_CUTLASS
```

Several other theoretically interesting MoE backends were unsupported or incompatible with this exact CUDA/SM120/EP3 combination, so random backend switching was stopped.

# Collective observation

NCCL debug showed an active decode AllGather of approximately:

```text
103,296 bytes
```

with:

```text
count:     51,648
protocol:  LL
algorithm: RING
channels:  4
```

The element count matches the padded per-rank vocabulary partition:

```text
154,944 / 3 = 51,648
```

The measured collective itself was only on the order of tens of microseconds, so removing it alone would not explain the several-percent gap between ~95.8 and 100 tok/s.

# v19 - KDA W8A16 / Humming optimization

v19 keeps the v18 TP3/EP3 geometry and shared-expert sharding, but converts one specific decode hotspot to FP8 weight-only execution:

```text
34 KDA layers
-> in_proj_qkvgfab only
-> BF16 checkpoint weight
-> per-output-channel FP8 E4M3 at runtime
-> BF16 activation
-> Humming W8A16 kernel
```

**Local image:** `voipmonitor/vllm:glm53-native-tp3-bf16-v19-kda-w8a16`

No checkpoint files are rewritten.

---

# Why this layer was targeted

The v18 PyTorch profiler mapped the largest single conventional CUDA family directly to the 34 KDA layers:

```text
34 calls / token
~15.3% of self CUDA time on the profiled TP rank
```

The corresponding layer is:

```text
in_proj_qkvgfab
```

Its local TP3 merged output geometry is:

```text
[2816, 2816, 2816, 22, 128]
```

which totals:

```text
8598 output values
```

The BF16 matrix is therefore approximately:

```text
8598 x 4096 x 2 bytes
~= 70.4 MB
```

per KDA layer per rank.

A cold-cache benchmark measured the BF16 projection at roughly the same latency as the real profiler:

```text
cold BF16 projection: ~47.7 us
real profiler:        ~45.4 us/call
```

Changing `F.linear` to `mm`, `matmul`, or `mv` produced no useful improvement. The operation was dominated by reading the BF16 weight matrix.

---

# Humming microbenchmark

A Humming W8A16 experiment was then tested with:

```text
activation: BF16
weight:     FP8 E4M3, per-output-channel scale
K:          4096
real N:     8598
```

Humming internally rounds N to a 256-wide physical shape and requires the logical padding remainder to be compatible with its kernel checks.

`N=8598` failed because the internal padding was not divisible by 8.

The smallest compatible logical width is:

```text
8598 -> 8600
```

so v19 adds only two synthetic output rows.

The successful synthetic benchmark measured:

```text
HOT BF16:       ~25.1 us
HOT Humming:    ~46.8 us

COLD BF16:      ~47.7 us projection time
COLD Humming:   ~30.7 us projection time

cold saving:    ~17.0 us/call
relative:       ~35.7%
34 KDA calls:   ~0.58 ms/token estimated saving
```

The hot benchmark is not representative of the real layer because the actual 70 MB KDA matrix is streamed from memory on every layer. The cold result matched the real profiler much more closely.

# v19 runtime geometry

The checkpoint and semantic KDA shape remain unchanged:

```text
checkpoint local BF16 weight: 8598 x 4096
semantic output width:        8598
```

After the normal checkpoint load, v19 performs an in-memory conversion:

```text
BF16 checkpoint weight [8598, 4096]
        |
        +-- append 2 zero output rows
        v
BF16 physical [8600, 4096]
        |
        +-- per-output-channel FP8 E4M3 quantization
        v
Humming W8A16 packed weight
        |
        +-- BF16 activation x FP8 weight
        v
8600 physical outputs
        |
        +-- discard last 2 synthetic outputs
        v
8598 semantic outputs
```

The two padded rows are zero before quantization and remain zero in the tested Humming path.

Nothing downstream sees the two synthetic channels.

---

# Scope of the quantization

Only this projection changes:

```text
KDA in_proj_qkvgfab
```

Everything else remains as in v18:

```text
KDA recurrent state:       unchanged
KDA f_b / g_a / g_b:       BF16
attention projections:     BF16
MLA:                       unchanged
shared experts:            BF16 TP-sharded
routed experts:            ModelOpt NVFP4
MTP:                       disabled
DFlash:                    disabled
KV cache:                   FP8
```

The on-disk LibertAIDAI checkpoint remains untouched.

# Integration detail

The GLM adapter intentionally creates KDA with a local copy of `VllmConfig` whose global checkpoint quantization is disabled. This is required because the fused KDA parameter name/geometry does not match the ModelOpt ignore metadata for the original checkpoint tensors.

v19 therefore does **not** re-enable global ModelOpt quantization for KDA.

Instead, it replaces the quant method only for `in_proj_qkvgfab` after the ordinary BF16 layer has been constructed and loaded.

Two integration issues were found during bring-up.

## 1. Post-load callback timing

Installing the experimental quant method after layer construction meant it was not part of vLLM's original `process_weights_after_loading()` callback registration.

The first version therefore reached forward with:

```text
GLM53 KDA W8A16 was used before process_weights_after_loading()
```

The final experimental implementation performs the conversion lazily on the first startup/profile forward, before normal serving and CUDA graph use.

## 2. vLLM config context

Constructing Humming creates a `QuantFP8` CustomOp, which expects an active current vLLM configuration.

The profile forward itself does not keep that configuration context active, so the first lazy implementation failed with:

```text
AssertionError: Current vLLM config is not set
```

v19 stores the KDA-local `VllmConfig` and temporarily restores it around Humming construction/weight processing using `set_current_vllm_config(...)`.

After that change the server loaded and served successfully.

# Long-form reasoning check

Two 4096-token technical prompts spent the entire completion budget in the `reasoning` field and returned:

```text
content:       None
finish_reason: length
```

The reasoning itself remained grammatically and technically coherent, but did not transition to the final-answer field before the token limit.

The identical HTTPS technical prompt was then run on v18 and produced the same behavior.

Conclusion:

```text
not a v19 W8A16 regression
```

This appears to be model/template/reasoning-parser behavior for that prompt style.

# Conclusion

v19 is the new confirmed native TP3/EP3 baseline.

The optimization is deliberately narrow: it converts only the 34 bandwidth-bound KDA merged input projections to FP8 weight-only Humming execution while preserving BF16 activations and leaving the checkpoint itself untouched.

It passed arithmetic correctness, normal Estonia 30/30, and Estonia-long 30/30 while improving generation speed by roughly 7-8% over v18.

The next remaining conventional performance targets are the 42-layer MoE path and MHC before enabling MTP/DFlash.

# v18 - TP-sharded shared expert

v18 replaces the replicated shared-expert workaround used by v14-v17 with a native TP3-sharded shared expert. It preserves the official checkpoint template, `glm45` reasoning parser, KDA/MLA padding, EP3 routed experts, FP8 KV cache, Triton KDA decode, and the otherwise known-good v17 serving configuration.

**Local image:** `voipmonitor/vllm:glm53-native-tp3-bf16-v18-shared-tp`

---

## Why v18 exists

The GLM-5.3 shared expert has an intermediate width of:

```text
2048
```

which is not divisible by TP3.

Through v17 the shared expert was therefore replicated on all three ranks with TP disabled. That was correct only after the v14 fix scaled each replicated shared-expert contribution by `1 / tp_size` before the generic TP SUM:

```text
rank 0: S / 3
rank 1: S / 3
rank 2: S / 3

TP SUM -> S
```

The workaround was numerically correct, but it kept a complete BF16 shared expert on every GPU.

v18 removes that replication.

---

# Shared-expert TP3 geometry

The logical intermediate width remains exactly:

```text
2048
```

For TP3, v18 pads the physical intermediate dimension to:

```text
2048 logical
-> 2052 physical
-> 684 channels / GPU
```

Only four physical intermediate channels are synthetic.

The effective rank layout is:

```text
rank 0: 684 real channels
rank 1: 684 real channels
rank 2: 680 real channels + 4 zero-padded channels
```

The shared expert now runs with TP enabled:

```text
disable_tp=False
reduce_results=False
```

and the old `1 / 3` shared-expert scaling is removed.

Each rank computes only its local intermediate shard, and the normal TP reduction reconstructs the final shared-expert output:

```text
rank 0 local shared output \
rank 1 local shared output  +-- TP SUM -> complete shared output
rank 2 local shared output /
```

This preserves the intended math without storing a complete shared expert on every rank.

Observed model-load memory:

```text

v18: ~59.5 GiB/GPU
```

Savings:

```text
~1.3 GiB/GPU
```


# Performance work around v18

The following areas were tested while establishing the v18 baseline:

```text
CUDA graphs off:                  ~7.4 tok/s -- unusably slow
custom all-reduce at world=3:     unsupported / no win
KDA decode auto vs Triton:        Triton retained
KDA B12X decode:                  slower
FlashInfer autotune:              retained
forced TRTLLM MoE:                invalid/unsupported
forced CuteDSL MoE:               invalid/unsupported
forced VLLM_CUTLASS MoE:          no useful win
router BF16x3:                    no useful win
NCCL protocol/channel tuning:     worse
B12X/FlashInfer custom AR:        unavailable at world=3
MLA split 32/auto:                best tested setting
```

The result was a stable baseline with most obvious runtime/backend knobs already explored.

# PyTorch profiler result

A 32-token decode trace showed the largest conventional decode costs on a representative TP rank were approximately:

```text
KDA merged BF16 projection:     15.31%
NCCL all-reduce:                10.96%
CUTLASS GEMM family:             9.23% + 5.75%
other GEMV / KDA projection:     several additional percent
MHC finalize:                    3.52%
MHC post/pre:                    2.51%
shared MLA:                      2.14%
BF16 -> FP4 conversion:          1.89%
```

The exact 34-calls/token hotspot mapped cleanly to the KDA merged projection:

```text
in_proj_qkvgfab
local shape: [4096 -> 8598]
weight size: ~70.4 MB BF16 / layer / rank
```

Cold-cache microbenchmarks closely matched the profiler and showed this projection to be strongly weight-bandwidth-bound. That profiling result directly motivated v19.
